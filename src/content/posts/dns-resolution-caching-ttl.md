브라우저에 도메인을 입력하고 페이지가 뜨기까지, 화면에 보이지 않는 곳에서 DNS가 여러 단계를 거쳐 IP 주소를 찾아온다. 이 글에서는 DNS가 어떤 데이터를 어떻게 저장하고, 어떤 순서로 질의하며, 왜 캐싱과 TTL 설계가 실무에서 중요한지를 `dig` 명령어와 코드로 직접 확인하면서 정리했다.

## DNS란

DNS(Domain Name System)는 전화번호부와 같다. 전화번호를 외우는 대신 이름으로 검색해서 번호를 찾듯이, IP 주소를 외우는 대신 도메인 이름으로 검색해서 IP를 찾을 수 있게 해준다. `142.251.23.100`을 기억하는 대신 `google.com`을 입력하면 되는 이유다.

## 리소스 레코드

DNS 서버가 보관하는 데이터를 리소스 레코드(RR, Resource Record)라고 부른다. 실제로 `dig` 명령어로 조회해보면 레코드가 어떤 필드로 구성되는지 바로 확인할 수 있다.

```bash
$ dig example.com A +noall +answer

example.com.        300     IN      A       104.20.23.154
example.com.        300     IN      A       172.66.147.243
```

(같은 A 타입 응답에 IP가 두 개 이상 오는 경우도 흔하다. 로드밸런싱 목적으로 여러 IP를 등록해두고, 클라이언트가 그중 하나를 골라 접속하게 하는 방식이다.)

각 필드는 다음을 의미한다.

- **이름(Name)**: 목적지 주소. 예) `example.com.`
- **TTL**: 초 단위 캐시 유효 시간. 예) `300`(5분)
- **클래스(Class)**: 네트워크 클래스. 현재는 인터넷(`IN`)만 사용해 대부분 그대로 표기된다.
- **타입(Type)**: 레코드가 처리하는 요청의 종류
- **값(Value)**: 실제 응답 데이터. 예) `104.20.23.154`

### 주요 레코드 타입

| 타입      | 역할                                                                   | 예시                                                     |
| --------- | ---------------------------------------------------------------------- | -------------------------------------------------------- |
| **A**     | 도메인에 대응하는 IPv4 주소                                            | `example.com. A 104.20.23.154`                           |
| **AAAA**  | 도메인에 대응하는 IPv6 주소                                            | `example.com. AAAA 2606:4700:10::6814:179a`              |
| **MX**    | 이메일을 받을 메일 교환 서버 지정, 숫자가 낮을수록 우선순위 높음       | `example.com. MX 10 mail.example.com.`                   |
| **NS**    | 해당 도메인을 관리하는 네임서버 주소. 안정성을 위해 보통 2개 이상 유지 | `example.com. NS hera.ns.cloudflare.com.`                |
| **CNAME** | 표준 도메인에 대한 별명(alias)                                         | `sports.naver.com. CNAME naver.com.`                     |
| **SOA**   | 도메인 관리자 메일, 시리얼 번호, 재시도 간격 등 메타 정보              | 아래 참고                                                |
| **TXT**   | 원래는 자유 메모용, 지금은 도메인 소유권 검증·스팸 방지에 사용         | `example.com. TXT "v=spf1 include:_spf.google.com ~all"` |

CNAME은 반드시 다른 도메인 이름을 가리켜야 하고, IP 주소를 직접 가리켜서는 안 된다는 제약이 있다. 그리고 CNAME이 걸린 이름에는 다른 타입의 레코드(A, MX 등)를 동시에 둘 수 없다는 규칙도 있다(**CNAME 배타 규칙**). 그래서 루트 도메인(`example.com` 자체)에는 CNAME을 쓸 수 없고, 서브도메인(`www.example.com`, `sports.naver.com` 등)에 주로 사용된다.

SOA 레코드는 조금 더 자세히 볼 가치가 있다.

```bash
$ dig example.com SOA +noall +answer

example.com. 1800 IN SOA elliott.ns.cloudflare.com. dns.cloudflare.com. (
                2411783310 ; serial   - 존(zone) 데이터 버전
                10000      ; refresh  - 보조 네임서버가 갱신을 확인하는 주기(초)
                2400       ; retry    - 갱신 실패 시 재시도 간격(초)
                604800     ; expire   - 이 기간 동안 갱신 못 하면 데이터를 폐기(초)
                1800 )     ; minimum  - 부정 응답(NXDOMAIN) 캐싱 시간(초)
```

(serial은 관례적으로 `YYYYMMDDnn` 형태의 날짜 기반 값을 쓰지만, 위 예시처럼 관리 주체가 자체 규칙의 정수 카운터를 쓰기도 한다. 보조 네임서버는 이 값이 이전에 본 값보다 커졌을 때만 존 데이터를 다시 가져간다.)

TXT 레코드가 소유권 증명에 쓰이는 대표적인 예는 SPF(이메일 발신자 검증), DKIM(서명 검증), 도메인 소유권 확인(`google-site-verification=...`) 같은 것들이다.

## 도메인 계층 구조

전 세계 모든 도메인의 IP를 하나의 서버가 보관하는 것은 불가능하다. 그래서 DNS는 트리 구조로 계층화되어 저장 부담을 분산한다. `www.example.com.`을 계층으로 풀어보면 다음과 같다.

```
                    .  (루트 도메인)
                    |
                  com  (TLD, 최상위 도메인)
                    |
              example  (2단계 도메인)
                    |
                  www  (3단계 = 서브도메인)
```

각 계층은 자신보다 하위 계층의 네임서버 주소만 알고 있다. 상위 서버에 물으면 "그건 모르지만, 답을 알 만한 하위 서버는 여기다"라고 알려주는 방식이다. 루트 네임서버는 전 세계에 13개의 논리적 그룹(`a.root-servers.net` ~ `m.root-servers.net`)으로 존재하며, 실제로는 애니캐스트로 수백 대의 물리 서버가 이 13개 주소를 나눠서 응답한다. 2002년과 2007년에 이 루트 서버 전체를 노린 대규모 DDoS 공격이 있었지만, 애니캐스트 분산 덕분에 서비스 중단으로는 이어지지 않았다.

## 질의 방식: 반복 vs 재귀

DNS 질의는 크게 두 가지 방식으로 이루어진다.

- **반복 질의(Iterative Query)**: 질의를 받은 서버가 답을 모르면, 직접 답을 찾아 나서는 대신 "나는 모른다, 대신 이 서버에 물어봐라"라며 다음으로 물어볼 서버 주소만 알려준다(리퍼럴). 질의를 보낸 쪽이 그 주소로 다시 직접 질의를 반복해야 한다.
- **재귀 질의(Recursive Query)**: 질의를 받은 서버가 답을 모르면, 자기가 대신 다음 서버에 질의를 넘기고 최종 결과를 받아와서 돌려준다. 질의를 보낸 쪽은 한 번만 물어보면 된다.

실무에서 이 둘은 구간별로 나뉘어 혼합된다. **클라이언트 ↔ 로컬 DNS 서버(리졸버)** 구간은 재귀 질의다. 클라이언트는 리졸버에게 한 번만 물어보고, 최종 IP를 받을 때까지 기다린다. 반면 **리졸버 ↔ 상위 네임서버(루트, TLD, 권한 서버)** 구간은 반복 질의다. 루트와 TLD 네임서버는 대부분 재귀 질의를 아예 받아주지 않도록 설정되어 있고("recursion not available"), 리퍼럴만 반환한다. 그래서 루트부터 권한 서버까지 발로 뛰며 반복 질의를 도맡아 하는 쪽은 리졸버 하나뿐이고, 그 결과만 클라이언트에게 재귀적으로 돌려주는 구조다. `dig +trace`로 이 반복 질의 과정을 직접 재현해볼 수 있다.

```bash
$ dig +trace example.com

;; 루트 네임서버가 .com을 담당하는 TLD 네임서버 목록으로 응답(리퍼럴)
com.                    172800  IN      NS      a.gtld-servers.net.
com.                    172800  IN      NS      b.gtld-servers.net.
...
;; Received ... from f.root-servers.net

;; TLD 네임서버가 example.com의 권한 네임서버로 응답(리퍼럴)
example.com.            172800  IN      NS      hera.ns.cloudflare.com.
example.com.            172800  IN      NS      elliott.ns.cloudflare.com.
;; Received ... from m.gtld-servers.net

;; 권한 네임서버가 최종 응답
example.com.            300     IN      A       104.20.23.154
example.com.            300     IN      A       172.66.147.243
;; Received ... from elliott.ns.cloudflare.com
```

클라이언트 입장에서는 리졸버 하나에만 물어보고 최종 결과를 기다리면 되니 구현이 단순하고, 리졸버가 그 과정에서 얻은 중간 결과(루트가 알려준 TLD 네임서버 주소, TLD가 알려준 권한 네임서버 주소 등)를 캐싱해두기 때문에 다음 질의부터는 반복 질의 단계를 일부 건너뛸 수 있다는 장점도 있다. 반면 리졸버가 누구에게나 재귀 질의를 받아주는 "오픈 리졸버"로 설정되어 있으면 다음과 같은 보안 위험이 따른다.

- **DNS 증폭 공격**: 오픈 리졸버에 출발지 IP를 피해자로 위조한 질의를 대량으로 보내면, 리졸버가 작은 질의보다 훨씬 큰 응답을 피해자에게 쏟아붓는 DDoS 공격이 성립한다.
- **DNS 캐시 포이즈닝**: 리졸버가 상위 서버에 반복 질의를 하는 과정에서 위조된 응답을 리졸버 캐시에 심으면, 이후 그 리졸버에 질의하는 모든 클라이언트가 가짜 IP로 유도된다.

## DNS 조회 전체 과정

브라우저에 `www.example.com`을 입력했을 때 실제로 벌어지는 순서다.

1. 클라이언트가 도메인 이름으로 접속을 시도한다.
2. **로컬 DNS 캐시** → **hosts 파일** → **라우터 캐시** 순으로 이미 알고 있는 값이 있는지 확인한다.
3. 캐시에 없으면 **로컬 DNS 서버**(ISP가 제공하거나 `8.8.8.8`, `1.1.1.1` 같은 공개 DNS)에 재귀 질의를 보낸다.
4. 로컬 DNS 서버도 캐시에 없으면 **루트 → TLD → 권한 네임서버** 순으로 반복 질의해 최종 IP를 얻는다.
5. 각 단계의 결과는 해당 위치에 캐싱되고, 최종 IP가 클라이언트에게 반환된다.

macOS나 Linux에서는 `dscacheutil`이나 `resolvectl` 같은 명령어로 로컬 DNS 캐시 상태를 직접 들여다볼 수 있다.

```bash
# macOS: DNS 캐시 조회
$ dscacheutil -q host -a name example.com

# macOS: DNS 캐시 전체 초기화 (문제 발생 시)
$ sudo dscacheutil -flushcache
$ sudo killall -HUP mDNSResponder

# Linux(systemd-resolved): 캐시 통계 확인
$ resolvectl statistics
```

공개 DNS를 쓰는 경우에도 `8.8.8.8`이 미국 캘리포니아의 특정 서버 하나로 연결되는 것이 아니다. **애니캐스트(Anycast) 라우팅** 덕분에 동일한 IP 주소가 전 세계 여러 지점에 동시에 할당되어 있고, BGP 라우팅상 나와 가장 가까운(hop 수가 가장 적은) 지점의 서버가 응답한다. 그래서 한국에서 `8.8.8.8`에 질의해도 실제로는 국내 또는 인접 지역의 엣지 서버가 응답을 준다.

## 캐싱이 일어나는 위치

DNS는 같은 도메인에 반복적으로 접근하는 경우가 많기 때문에 여러 단계에서 캐싱한다. 조회 속도가 빠른 순서대로 정리하면 다음과 같다.

1. **로컬 DNS 캐시(캐시 테이블)**: OS 메모리에 존재하며 가장 먼저 조회되는 캐시. 브라우저 자체도 별도의 DNS 캐시를 갖고 있어서(크롬은 `chrome://net-internals/#dns`에서 확인 가능), 실제로는 브라우저 캐시 → OS 캐시 순으로 확인된다.
2. **hosts 파일**: 보조기억장치(디스크)에 저장된 파일로, 네임서버가 등장하기 전 호스트 이름과 IP를 직접 매핑하던 방식이다. macOS/Linux는 `/etc/hosts`, 윈도우는 `C:\Windows\System32\drivers\etc\hosts`에 위치한다. 지금은 잘 쓰이지 않지만 네임서버 조회보다 우선순위가 높아서, 로컬 개발 환경에서 도메인을 특정 IP로 강제로 매핑할 때 여전히 활용된다.

```
# /etc/hosts 예시 — 로컬 개발 시 도메인을 특정 IP로 강제 매핑
127.0.0.1   dev.example.com
```

3. **라우터 캐시**: DNS 질의가 나가는 길목의 공유기/라우터가 이미 아는 정보라면 라우터 단계에서 바로 응답할 수 있다.
4. **로컬 DNS 서버(ISP 또는 공개 DNS)**: 이미 캐싱된 정보면 바로 반환하고, 없으면 반복/재귀 질의로 IP를 가져와 캐싱한 뒤 반환한다.

## TTL(Time To Live)

각 리소스 레코드에는 초 단위 TTL이 설정되어 있고, 이 값이 캐시 유효 시간을 결정한다. 권한 네임서버가 응답할 때 TTL도 함께 전달하며, TTL이 지나면 캐시가 만료되어 다시 조회한다.

TTL 값에 따른 트레이드오프는 명확하다.

| TTL 설정                | 장점                                    | 단점                                                 |
| ----------------------- | --------------------------------------- | ---------------------------------------------------- |
| 짧게 (예: 60~300초)     | IP 변경이 빠르게 전파됨                 | 리졸버가 매번 다시 질의해야 해서 조회 부하·지연 증가 |
| 길게 (예: 86400초 이상) | 캐시 적중률이 높아 부하 감소, 응답 빠름 | IP 변경이 전 세계에 반영되기까지 오래 걸림           |

그래서 실무에서는 **서버 이전이나 로드밸런서 교체처럼 IP가 바뀔 예정이라면, 변경 며칠 전에 미리 TTL을 짧게(예: 60초) 낮춰두고, 변경이 완전히 전파된 뒤 다시 원래 값으로 늘리는 절차**를 따른다. 이렇게 하지 않으면 일부 사용자는 며칠간 옛날 IP로 계속 요청을 보내게 된다.

Node.js에서 TTL이 실제로 어떻게 동작하는지 간단히 확인해볼 수 있다. `dns.resolve4`는 레코드와 함께 TTL을 반환한다.

```js
import dns from "node:dns/promises";

const resolver = new dns.Resolver();
const records = await resolver.resolve4("example.com", { ttl: true });

console.log(records);
// [
//   { address: '104.20.23.154', ttl: 300 },
//   { address: '172.66.147.243', ttl: 300 }
// ]
```

이를 이용해 TTL만큼만 캐시를 유지하는 간단한 리졸버 캐시를 흉내 내볼 수도 있다.

```js
const cache = new Map();

async function resolveWithCache(hostname) {
  const cached = cache.get(hostname);
  const now = Date.now();

  if (cached && cached.expiresAt > now) {
    return cached.address; // 캐시 적중, DNS 질의 없이 반환
  }

  const [record] = await resolver.resolve4(hostname, { ttl: true });
  cache.set(hostname, {
    address: record.address,
    expiresAt: now + record.ttl * 1000,
  });

  return record.address;
}
```

TTL이 지나기 전까지는 네트워크 질의 없이 캐시에서 바로 응답하고, 지난 뒤에만 다시 리졸버에 물어보는 구조다. 실제 OS 리졸버와 브라우저도 근본적으로 이와 같은 방식으로 동작한다.

## 보안

### 주요 위협

- **DNS 스푸핑 / 캐시 포이즈닝**: 위조된 응답을 리졸버 캐시에 주입해 사용자를 가짜 IP로 유도하는 공격. 질의 ID(Transaction ID)와 출발지 포트를 예측해 정당한 응답보다 먼저 위조 응답을 끼워 넣는 방식이 대표적이다.
- **DNS 증폭 공격**: 재귀 질의 구조를 악용해 위조된 출발지 IP로 대량 질의를 보내, 하나의 서버(피해자)에 응답 트래픽이 집중되도록 유도하는 DDoS 공격.
- **DNS 하이재킹**: 도메인 등록 정보나 네임서버 설정 자체를 탈취해 트래픽을 통째로 가로채는 공격. 레지스트라 계정 탈취, 등록 이관 사기 등이 여기 해당한다.

### 방어 기술

- **DNSSEC**: 응답에 전자서명을 추가해 위변조 여부를 검증할 수 있게 하는 확장. 기존 DNS는 암호화·인증 메커니즘이 전혀 없어 스푸핑에 취약했는데, DNSSEC은 상위 존(zone)이 하위 존의 공개키를 서명하는 신뢰 체인(chain of trust)을 루트부터 이어가며 이 문제를 보완한다. `dig` 명령어에 `+dnssec` 플래그를 주면 서명(RRSIG) 레코드를 확인할 수 있다.
- **DoH(DNS over HTTPS)**: DNS 쿼리를 HTTPS로 암호화해 전송, 포트 443 사용. 일반 HTTPS 트래픽과 구분이 어려워 방화벽/필터링 우회에 활용되기도 한다는 점이 논쟁거리다.
- **DoT(DNS over TLS)**: DNS 쿼리를 TLS로 암호화해 전송, 별도 포트(853) 사용. DoH와 달리 포트가 구분되어 있어 네트워크 관리자가 DNS 트래픽만 식별·정책 적용하기 쉽다.

DoH와 DoT는 통신 구간의 도청과 변조를 막는 데 초점이 있고, DNSSEC은 응답 자체가 진짜인지 검증하는 데 초점이 있다. 즉 DoH/DoT는 "누가 엿보거나 바꿔치기하지 못하게" 만드는 것이고, DNSSEC은 "이 응답이 진짜 권한 서버가 서명한 것이 맞는지" 확인하는 것이라서 목적이 다르며, 실제로는 함께 적용된다.
